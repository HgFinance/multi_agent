# 스킬 쓰기 — 뚫은 것을 남긴다

## 왜 네가 이걸 하나

병목을 뚫는 것과 **다시 안 막히게 하는 것**은 다른 일이다. 뚫기만 하면
다음 주기의 네가(또는 다른 부서가) 같은 자리에서 같은 시간을 태운다.

2026-08-12 하루에 배관 결함 열두 건이 났다. **전부 데이터도 구현도 이미
있었다.** 그런데 매번 "없다" 로 읽혔다. 한 번 찾은 사람이 그것을 남겼으면
나머지 열한 번은 안 났다.

| 그날 나온 말 | 실제 |
|---|---|
| `'low_volatility' 전략 구현 필요` | 구현은 8종 다 있었다 |
| `실행면이 노출되지 않았다` | 있었다. 스킬이 실행을 금지하고 있었다 |
| `source_registry.py: ABSENT` | 54,905바이트로 있었다. 경로가 `/app/repo` |
| `BadGzipFile` | 파일 멀쩡. 명세 조회가 빗나가 gzip 리더로 떨어졌다 |

## 언제 쓰나 — 그리고 언제 안 쓰나

**쓴다:**
- 같은 종류의 문제를 **두 번** 만났다
- 남들이(또는 네가) "없다/안 된다" 고 오진하던 것을 사실로 밝혔다
- 절차가 있는데 아무도 몰라서 안 쓰이고 있다
- 네 판단이 매번 같은 규칙을 따르고 있다 — 그러면 그건 규칙이지 판단이 아니다

**안 쓴다:**
- 한 번 난 일회성 사고 — 그건 카드 노트에 적을 일이다
- 코드를 읽으면 5분 안에 알 수 있는 것 — 스킬은 코드의 사본이 아니다
- 아직 안 해 본 것 — **해 보지 않은 절차를 스킬로 쓰면 다음 사람을 더 멀리
  돌아가게 한다.** 오늘 그런 스킬이 실제로 실행을 금지해 카드를 죽였다

## 무엇이 좋은 스킬인가

**증상에서 시작한다.** 사람은 "무엇을 해야 하나" 가 아니라 "이게 왜 안 되지"
로 도구를 찾는다. 첫 절이 증상 목록이어야 검색에 걸린다.

**실측을 싣는다.** "이럴 수 있다" 가 아니라 "이랬다". 날짜와 수를 적어라.
읽는 쪽이 자기 상황과 대조할 수 있어야 한다.

```
나쁨: 경로 문제가 있을 수 있으니 확인하세요
좋음: `source_registry.py: ABSENT` 로 카드가 죽었다. 파일은
      /app/repo/... 에 54,905바이트로 있었다. 155초를 태웠다
```

**돌릴 수 있는 것을 준다.** 설명만 있는 스킬은 안 읽힌다. 한 줄 명령이
있어야 쓴다. 경로는 `find` 로 잡아라 — 박아 두면 구조가 바뀔 때
"스킬이 없다" 로 읽힌다.

```bash
SKILLDIR=$(find /opt/data -type d -name <스킬이름> | head -1)
quant-py "$SKILLDIR/scripts/<도구>.py"
```

**하지 않을 것을 적는다.** 스킬의 절반은 금지다. 무엇을 하지 말아야 하는지
없으면 사람은 가장 빠른 길로 간다 — 그게 대개 틀린 길이다.

## 절차

### 1. 사고 원문을 먼저 적는다

고친 뒤에는 원인이 당연해 보여서 **증상을 잊는다.** 증상이 없으면 다음
사람은 그 스킬을 못 찾는다. 실제 예외 메시지·로그 줄을 그대로 붙여라.

### 2. 쓴다

```
skills/<이름>/
  SKILL.md              # frontmatter: name, description, version, metadata.hermes
  scripts/<도구>.py      # 있으면
```

`description` 이 검색 열쇠다. **증상 문장을 넣어라** — "언제 쓰는지" 가
description 에 없으면 아무도 안 부른다.

### 3. 도구를 붙였으면 실제로 돌려 본다

**돌려 보지 않은 명령을 스킬에 적지 않는다.** 오늘 스킬에 적힌 경로가
컨테이너에서 한 겹 더 들어가 있어 안 먹은 일이 있었다. 컨테이너 안에서
그대로 복붙해 돌아가는지 확인해라.

```bash
docker exec <컨테이너> quant-py "$SKILLDIR/scripts/<도구>.py" --help
```

### 4. 재발하면 실패하는 검사를 남긴다

스킬은 사람이 읽어야 작동한다. **검사는 안 읽어도 작동한다.** 둘 다 필요하다.

고친 코드 쪽에 자체 점검을 넣되, **그 검사가 자기 사고를 실제로 잡는지**
확인해라. 사고 문장 원문을 픽스처로 넣으면 확실하다.

```python
def _check_<사고이름>():
    """<사고 원문 한 줄>. (YYYY-MM-DD 실측)"""
    # ▶ 검사가 사고를 잡는지 먼저 확인한다 - 안 잡는 검사는 아무것도 안 지킨다
    assert _detect(사고_픽스처), "검사가 사고 원문을 못 잡는다"
    assert not _detect(현재_코드), "..."
```

"검사를 만들었다" 와 "그 검사가 그 사고를 잡는다" 는 다르다. 실제로 정규식이
자기가 만들어진 사고 문장을 못 잡은 일이 있었다.

### 5. 프로필에 설치한다

```bash
# 프로필 구조가 한 겹 더 들어가 있을 수 있다 - 실측으로 잡는다
DEST=$(find /opt/data -type d -name skills | head -1)
cp -r skills/<이름> "$DEST/"
find /opt/data -path "*<이름>*"          # 들어갔는지 확인
```

### 6. 이어 놓는다

새 스킬은 **관련 스킬에서 가리켜야** 발견된다. `metadata.hermes.related_skills`
에 적고, 관련 스킬 본문에도 한 줄 링크를 넣어라. 아무도 안 가리키는 스킬은
없는 것과 같다.

## 성과를 올리는 스킬로 넘어갈 때

병목을 스스로 뚫게 되면 그다음은 **결과를 올리는 것**이다. 그때 쓰는 스킬은
성질이 다르다.

| 병목 스킬 | 성과 스킬 |
|---|---|
| "왜 안 되나" 를 사실로 만든다 | "무엇이 더 나은가" 를 사실로 만든다 |
| 층별 진단, 경로 확인 | 대조군, 반복, 판정 기준 |
| 성공 = 막힌 곳을 찾음 | 성공 = **측정된 개선** |

성과 스킬을 쓸 때 반드시 갖출 것:

- **무엇과 비교하는가.** 대조군 없는 "개선" 은 개선이 아니다
- **몇 번 시도했는가.** 여러 번 돌려 고른 최고치는 실력과 운을 못 가린다
  (`trial_family` 가 이미 세고 있고 DSR 이 그만큼 깎는다)
- **미측정과 0 의 구분.** 안 잰 것을 0으로 적으면 판정이 오염된다
- **되돌리기 금지.** 결과가 나쁘면 그것도 결과다. 코드를 되돌려 좋은 쪽만
  고르면 그건 결과가 아니라 선택이다

**성과 스킬을 쓰기 전에 그 개선을 한 번은 실제로 측정해 봐라.** 측정해 보지
않은 개선법을 스킬로 쓰면, 다음 사람이 그것을 근거로 삼는다.

## 하지 않을 것

**절차를 지어내지 않는다.** 돌려 보지 않은 명령, 열어 보지 않은 경로,
확인하지 않은 계약은 스킬에 넣지 않는다. 스킬은 다음 사람이 **믿고 따르는**
문서다 — 여기서 지어내면 오진이 증폭된다.

**코드를 옮겨 적지 않는다.** 스킬은 코드가 어디 있고 왜 그렇게 되어 있는지를
말한다. 구현을 복사하면 코드가 바뀔 때 스킬이 거짓말을 시작한다.

**금지만 적지 않는다.** "하지 마라" 만 있고 "그럼 무엇을" 이 없으면 사람은
막힌 채로 카드를 닫는다. 오늘 실행을 금지하기만 한 스킬이 실제로 그랬다.

**한 스킬에 다 넣지 않는다.** 진단·구축·판정은 다른 일이다. 섞으면 아무도
끝까지 안 읽는다.
