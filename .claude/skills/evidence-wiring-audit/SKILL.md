# Evidence Wiring Audit

수집기가 넣은 데이터가 분석가에게 도달하는 경로를 끝까지 따라가, **중간에서 조용히 사라지는 지점**을 찾는다.

## 왜 이 스킬이 필요한가

멀티에이전트 파이프라인은 층이 많다.

```
수집기 → DB → API SELECT → 도구/클라이언트 → 분석가 readout
      → 총괄 프롬프트 → 검증 가드 → 리포트
```

층마다 **조용히 떨어뜨릴 수 있다.** 예외가 안 나고, 로그도 안 남고, 그냥 값이 없거나 0이 된다. 그러면 겉으로는 이렇게 보인다.

| 증상 | 실제 원인 (실측 사례) |
|---|---|
| "지표가 부족해 근거가 부실하다" | `/bars` SELECT에 `notional`이 없어 Amihud가 **영구 `None`** — 레지스트리엔 `ADOPTED`로 등재 |
| "가드가 정상 인용을 창작으로 몬다" | 정규식 `\d{1,3}` 상한 때문에 `-29.8837%`를 **`837`로 잘라 읽음** |
| "LLM이 서술을 안 한다" | 분석가는 `summary`를 최상위로 내는데 파이프라인은 `note.summary`만 읽어 **매 실행 100% 폐기** |
| "도구를 줬는데 안 쓴다" | 러너가 `?code=`를 보내는데 API는 `codes=`를 받아 **매번 422** |
| "과거 비교가 이상하다" | `?date=`가 무시돼 **매번 오늘 자신과 비교** |
| "심리 지표가 전부 미확인" | `/macro` SELECT에 `metadata`가 없어 52주 위치가 안 나감 |

**한 세션에서 이 유형만 8건 나왔다.** 전부 데이터는 이미 있었고, 새 수집기도 새 라이브러리도 필요 없었다. 그런데 증상만 보면 모델·프롬프트·지표 설계 문제로 보인다 — 그래서 엉뚱한 곳을 고치게 된다.

## 작업 순서

### 1. 기계적 스캔부터 (스크립트가 한다)

사람 눈으로 찾을 것이 아니다. 먼저 돌린다:

```bash
python .claude/skills/evidence-wiring-audit/scripts/scan_wiring.py <저장소_루트>
```

찾는 것:
- **DB 컬럼 vs SELECT**: 마이그레이션에 있는데 어떤 SELECT에도 안 나오는 컬럼
- **자릿수 상한 정규식**: `\d{1,N}` 형태 — 수치를 잘라 읽는다
- **키 접근 불일치**: `r.get("note")` 하는데 반환은 평평한 `summary`인 경우
- **쿼리 파라미터**: 클라이언트가 보내는 이름 vs 엔드포인트가 받는 이름
- **정렬 가정**: `[-1]`을 "최신"으로 쓰면서 정렬을 안 하는 경우

스크립트는 **후보를 낼 뿐 판정하지 않는다.** 오탐이 있으니 다음 단계에서 확인한다.

### 2. 실제로 값이 오는지 확인 (동적)

정적 스캔은 "없어 보이는 것"을 찾고, 여기서 "정말 없는지"를 본다. 서비스가 떠 있으면 실제로 부른다.

```python
# 예: 필드가 응답에 실제로 오는가
r = get_json(".../bars/005380?limit=3")
print(sorted(r[0]))          # 키 목록을 눈으로 확인
```

**중요**: 컨테이너로 도는 서비스는 코드를 고쳐도 **이미지에 굽힌 옛 코드**를 쓴다. `docker compose up -d --build`로 재빌드하지 않으면 "고쳤는데 안 바뀐다"에 시간을 태운다.

### 3. 파생 계산이 살아나는지 확인

컬럼 하나가 막히면 그것을 쓰는 계산이 통째로 죽는다. 값이 온 뒤 **그 계산을 실제로 돌려본다.**

```python
r = compute_liquidity(bars)
assert r.get("amihud") is not None, "컬럼은 왔는데 계산이 여전히 None"
```

### 4. 자체점검에 고정한다

찾은 결함마다 **재발하면 실패하는 검사**를 남긴다. 고치기만 하면 다음에 또 난다.

검사가 자기 사고를 잡는지 확인한다 — 실제로 시점 가드를 만들었는데 정규식이 연도 뒤 구분자를 요구해서 **자기가 만들어진 사고 문장을 못 잡은 일**이 있었다. 사고 문장 원문을 픽스처로 넣으면 그런 일이 없다.

## 판정 원칙

**계산 못 한 것과 값이 0인 것을 구분한다.** `None`을 0으로 채우면 두 상태가 섞이고, 그 순간 판정이 오염된다. 못 구했으면 키에서 빼고 `unavailable`에 이름을 남긴다 — 무엇이 빠졌는지 보여야 사람이 판단한다.

**행 0을 정상 0으로 위장하지 않는다.** 빈 응답은 `ok=False` + 사유다. 사유 없는 실패는 만들 수 없게 계약으로 막는다.

**선언과 실재를 대조한다.** 레지스트리에 `ADOPTED`라고 적고 값이 안 나오는 상태가 가장 나쁘다 — 있다고 믿고 쓰기 때문이다. 선언한 것이 실제로 도는지 검사가 확인해야 한다.

**가드가 정상 인용을 위반으로 몰면 사람이 가드를 무시한다.** 오탐은 단순한 소음이 아니라 가드 전체를 무력화한다. 가드를 만들 때는 정상 사례를 픽스처에 함께 넣는다.

## 배관을 늘릴 때 같이 늘어나는 것

확정치 풀(검증 화이트리스트)이 넓어지면 **우연히 맞는 수치**가 생긴다. 지표를 10개에서 31개로 늘리자 창작 수치가 두 지표에 동시에 걸려 통과한 일이 있다.

그래서 "불일치 0"만으로는 부족하다. **어느 키에 맞았는지**를 남겨 모호 비율을 함께 봐야 한다.

```
40.0%   → momentum_20d_pct 하나   (검증)
99.9%   → adx, rsi 둘            (모호 — 통과했지만 우연일 수 있다)
4444.4% → 없음                    (창작)
```

배관을 뚫는 작업과 검증을 조이는 작업은 **같이 가야 한다.** 한쪽만 하면 느슨해진 것을 모른 채 좋아 보이는 숫자만 남는다.

## 보고 형식

찾은 것마다 이렇게 적는다. 증상이 아니라 **경로:행과 재현**을 적어야 다음 사람이 확인할 수 있다.

```markdown
### <한 줄 증상>
- 위치: <파일 경로:행>
- 원인: <무엇이 어디서 떨어지는가>
- 재현: <실제로 돌려본 명령과 그 출력>
- 영향: <어느 분석가/지표가 죽어 있었나>
- 고침: <무엇을 바꿨나>
- 재발 방지: <추가한 자체점검 이름>
```

## 하지 않을 것

**추측으로 채우지 않는다.** 필드가 없으면 없는 것이고, 기본값을 만들어 넣으면 "없다"는 사실이 사라진다.

**한 번에 다 고치지 않는다.** 배관 결함은 서로 얽혀 있어서, 하나 고치면 다음 것이 드러난다. 고칠 때마다 실제로 돌려 확인하고 다음으로 간다 — 다섯 개를 한꺼번에 바꾸면 무엇이 효과가 있었는지 알 수 없다.

**증상을 원인으로 착각하지 않는다.** "지표가 부족하다"는 결론이 아니라 출발점이다. 지표를 새로 만들기 전에 **이미 있는 것이 도달하고 있는지** 먼저 본다.
